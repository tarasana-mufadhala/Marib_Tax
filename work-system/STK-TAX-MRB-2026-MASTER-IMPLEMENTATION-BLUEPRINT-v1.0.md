# الملخص التنفيذي

هذا المستند هو المرجع الرسمي الذي يحول المتطلبات الوظيفية المعتمدة لنظام مكتب الضرائب بمحافظة مأرب إلى مخطط هندسي وتنفيذي قابل للبناء والاختبار والتسليم. يتكون النظام من تطبيق Flutter للمكلفين، وموقع عام ولوحة إدارة مبنيين بـ Next.js، وخلفية NestJS بنمط Modular Monolith، وقاعدة PostgreSQL مُدارة عبر Supabase، وتخزين خاص للمرفقات، وTwilio SMS للتحقق والإشعارات الخارجية في الإصدار الأول، وFirebase Cloud Messaging للتنبيهات الفورية.

الخطة تتجنب تكرار أخطاء المشاريع السابقة من خلال تثبيت قواعد العمل قبل البرمجة، وفصل الحساب عن المكلف، وإصدار نسخ للخدمات ومتطلباتها، وحفظ التاريخ الكامل للحالات والقرارات، ومنع الاتصال المباشر من العملاء بقاعدة البيانات التشغيلية، واستخدام Outbox للرسائل، وربط كل تقرير بتعريف بيانات موحد، وفرض Pull Requests واختبارات مطلوبة قبل الدمج.

# 1. الغرض والسلطة والنطاق

## 1.1 الغرض

يحدد هذا المخطط كيف سيُبنى النظام، وأين توضع قواعد الأعمال، وكيف تُدار البيانات والصلاحيات والملفات والتكاملات والتقارير، وكيف تقسم مراحل التنفيذ، وما الشروط التي تمنع الانتقال من مرحلة إلى أخرى. وهو مرجع للمطورين وCursor والمختبرين ومدير المشروع وصاحب المنتج ومكتب الضرائب.

## 1.2 سلطة المستند

* أي سلوك لا يطابق هذا المستند يُعد انحرافًا يحتاج طلب تغيير رسميًا.
* الشاشات لا تُعد مصدر الحقيقة؛ مصدر الحقيقة هو قواعد المجال وعقد API وقاعدة البيانات.
* لا يسمح لـ Cursor أو أي مساعد برمجي بابتكار متطلبات أو حالات أو جداول خارج النطاق دون اعتماد.
* أي قرار تفصيلي جديد يُسجل في ADR أو سجل قرار الأعمال، ويربط بالمتطلب والاختبار المتأثر.

## 1.3 أهداف النجاح

| **الهدف** | **مؤشر النجاح** |
| --- | --- |

| سلامة البيانات | عدم وصول مستخدم إلى بيانات أو مرفقات مستخدم آخر؛ وعدم ضياع التاريخ. |

# 2. المبادئ الحاكمة والقرارات غير القابلة للتفاوض

| **الرمز** | **المبدأ** | **التطبيق الإلزامي** |
| --- | --- | --- |
| P-01 | المجال أولًا | قواعد الضرائب والمعاملات تكتب كخدمات مجال واختبارات، لا كمنطق متفرق في الشاشات. |
| P-02 | لا اتصال مباشر بالبيانات | Flutter وNext.js لا ينفذان عمليات تشغيلية مباشرة على جداول قاعدة البيانات؛ تمر العمليات عبر API. |
| P-03 | التاريخ لا يُمحى | الحالات والقرارات والملكية والعناوين والمبالغ تحفظ تاريخيًا؛ التصحيح بنسخة/حدث جديد. |
| P-04 | أقل صلاحية | كل دور وخدمة وقاعدة بيانات تعمل بأقل صلاحيات لازمة، مع RLS كدفاع إضافي. |
| P-05 | الرسائل غير متزامنة | فشل Twilio أو FCM لا يفشل الطلب؛ يسجل الإرسال ويعاد عبر Worker. |
| P-06 | الخدمات ذات إصدارات | تغيير متطلبات خدمة لا يغير الطلبات القديمة؛ كل طلب يحتفظ بنسخة المتطلبات. |
| P-07 | بيانات قليلة تكفي | لا تجمع بيانات شخصية للعمال أو المستأجرين؛ يكتفى بالأعداد حسب القرار المعتمد. |
| P-08 | لا حذف تشغيلي | المعاملات المرسلة لا تُحذف ولا تُلغى من المكلف؛ تغلق أو تؤرشف إداريًا بسبب موثق. |
| P-09 | التقارير من سجل موثوق | كل مؤشر له تعريف ومصدر وتاريخ احتساب واختبار مطابقة. |
| P-10 | AI تحت المراجعة | مخرجات Cursor لا تدمج دون مراجعة بشرية واختبارات وCI ناجح. |

## 5.1 مكونات التقنية

## 6.3 ضوابط الموظفين

* جلسات أقصر وتسجيل الجهاز ومحاولات الدخول.
* تعطيل فوري للحساب وإبطال الجلسات.
* كل عملية حساسة تتطلب سببًا وتُسجل قبل/بعد.

## 8.1 نمط إنشاء الطلب

1. إنشاء draft مرتبط بإصدار الخدمة الحالي.
2. حفظ النموذج محليًا وعلى الخادم بشكل تدريجي مع idempotency.

## 11.2 قواعد خاصة

# 12. المستحقات والسداد

## 12.1 مصدر البيانات ومسؤوليتها

الأدمن يستلم المستندات الداخلية المكتملة توقيعًا واعتمادًا، ويدخل المبلغ الصحيح ويرفع مستند أحقية المبلغ. بعد السداد اليدوي يستلم الإيصال ويرفعه ويثبت السداد. لا يوجد نظام مالي خارجي ولا بوابة دفع ولا اعتماد إلكتروني إضافي من مدير.

## 12.2 التدفق

1. إنشاء due بمبلغ وسبب ومستند أساس واسم المدخل.
2. تحويل الطلب إلى payment\_required وإنشاء إشعار.
3. السداد خارج النظام.
4. رفع إيصال السداد وإنشاء payment\_record.
5. لا تتحول الحالة إلى paid دون إيصال.
6. إعادة الطلب للمسار السابق أو المحدد بعد السداد.

## 12.3 التصحيح

| **المرحلة** | **السياسة** |
| --- | --- |
| قبل إشعار المكلف | تعديل مسموح مع Audit. |
| بعد الإشعار وقبل السداد | تصحيح بسبب ومستند جديد وحفظ السابق وإشعار مصحح. |
| بعد السداد | لا تعديل مباشر؛ financial\_correction مستقل مع سبب واعتماد وصورة كاملة للتاريخ. |
